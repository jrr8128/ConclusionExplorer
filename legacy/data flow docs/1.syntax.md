# Game of Logic — Phase 1 Control/Data-Flow Trace

> Goal: explain the **high-level flow** (what happens, in what order), the **data flow** (what is stored where and why), and the **invariants** that make the implementation fast and reliable.

## 0. Glossary and ID rules

> **Terminology note:** This document uses the word **rule** instead of “invariant.” A **rule** is something that must be true if the data is valid (and the code assumes it).

### 0.1 Terms

* **term_id**: integer in `[0, term_count)`.
* **term_literal**: `(term_id, is_complement)` meaning `T` or `¬T`.

### 0.2 Statements

* **form**: `A, E, I, O` meaning:

  * **A**: All S are P
  * **E**: No S are P
  * **I**: Some S are P
  * **O**: Some S are not P
* **statement**: `(form, subject_literal, predicate_literal)`.

### 0.3 IDs (strong typedefs)

* **statement_id (sid)**: dense ID; `sid.id` is an index into `all_statements`.
* **premise_id (pid)**: **same numeric domain as `statement_id`**; used for readability only.

  * **Rule:** In phase 1, `pid.id == sid.id` whenever they reference the same underlying statement.
  * **Rule:** Never treat premise IDs as class IDs or requirement IDs.
* **class_id (cid)**: dense equivalence-class ID.
* **representative_id (rep_id)**: alias of `statement_id` used as the class representative.

### 0.4 Later IDs (reserved terms)

* **requirement_index (rid / req_index)**: dense index for “required nonempty region” constraints (NOT a statement id).
* **region_bit (rb)**: bit index representing a semantic region.

## 1. Syntax stage (`build_syntax_space` → `syntax_space`)

### 1.1 Purpose (plain-English)

Generate the full AEIO statement catalog for a fixed `term_count`, then collapse statements that mean the same thing into equivalence classes. Search later iterates one representative per class to avoid redundant work.

Why this exists:

* Ensures the search explores the **logical space**, not redundant surface phrasing.
* Produces stable dense IDs so later phases can store/print/compare efficiently.

### 1.2 Output structure (`syntax_space`)

* `term_count`: number of base terms.
* `all_statements`: global catalog; `statement_id` is the index into this vector.
* `class_id_by_statement_id`: maps each `sid` → its `cid`.
* `rep_id_by_class_id`: maps each `cid` → a chosen representative `sid` (the search list).

### 1.3 Rules (must hold after build)

* `3 ≤ term_count ≤ 8`.
* `class_id_by_statement_id.size() == all_statements.size()`.
* `cid.id` are dense: `0..(rep_id_by_class_id.size()-1)`.
* For each `cid`, `rep_id_by_class_id[cid]` is the **first-seen** `sid` assigned to that class.
* For any valid `sid`, `sid.id < all_statements.size()`.

### 1.4 Equivalence definition (why reps are safe)

Equivalence is defined by a canonical key derived from a statement:

* Rewrite to **E/I-only** keys:

  * `A(S,P) ≡ E(S, ¬P)`
  * `O(S,P) ≡ I(S, ¬P)`
* Symmetry:

  * `E(S,P) == E(P,S)`
  * `I(S,P) == I(P,S)`
* Canonical key format:

  * form is always `E` or `I`
  * `(subject, predicate)` ordered so `subject <= predicate` under `term_literal` ordering

Consequence:

* Each equivalence class represents one unique logical constraint; iterating only representatives preserves completeness.

### 1.5 Build pipeline (exact step ordering)

> **Deterministic ordering (what it means):** For a given `term_count`, the loops enumerate statements in the same order every run. That makes `statement_id` assignments repeatable, which improves debugging, testing, memoization keys, and reproducible outputs.
> Inside `build_statements(syntax_space&)`:

1. Create build-time hash map `canonical_key -> class_id`.
2. Enumerate statements in stable nested-loop order:

   * `form ∈ {A,E,I,O}`
   * `subject_term ∈ [0, term_count)`; `subject_is_complement ∈ {false,true}`
   * `predicate_term ∈ [0, term_count)`; `predicate_is_complement ∈ {false,true}`
3. **Prune degenerate same-base-term pairs**: skip if `subject_term == predicate_term`.
4. For `E` and `I`, **prune symmetric duplicates** during generation: if `predicate_literal < subject_literal`, skip.
5. Append the statement to `all_statements`.
6. Define `sid = index_of_appended_statement`.
7. Compute canonical equivalence key (`canonical_equiv_statement`).
8. Get or create `cid`:

   * if new key: assign `cid = rep_id_by_class_id.size()` and push `sid` as representative
   * else: reuse existing `cid`
9. Append `cid` to `class_id_by_statement_id` (kept aligned with `all_statements`).

Inside `build_syntax_space(term_count)`:

1. Assert term_count range.
2. Initialize `syntax_space` (store term_count).
3. Call `build_statements`.
4. Return `syntax_space`.

### 1.6 Why this is lean/fast

* Dense IDs allow vectors everywhere in hot paths.
* Deterministic ordering makes IDs and outputs reproducible.
* Canonicalization collapses redundant statement variants.
* Early pruning avoids generating/searching useless trivial statements.

### 1.7 What the optimizations buy (rough counts)

Let `n = term_count` and `L = 2n` be the number of literals including complements.

**Without any pruning/collapsing** (naive surface enumeration):

* Forms: 4
* Ordered literal pairs (S,P) with `S != P`: `L*(L-1)`
* Total: `4 * L*(L-1) = 4*(2n)*(2n-1) = 8n(2n-1)`

**After same-base-term pruning** (`subject.term != predicate.term`):

* For each subject literal, predicate cannot be the same base term (two literals: T and ¬T), so predicate choices per subject: `L-2`.
* Total: `4 * L*(L-2) = 4*(2n)*(2n-2) = 16n(n-1)`.
* Compared to naive: ratio = `(L-2)/(L-1) = (2n-2)/(2n-1)`.

**After E/I symmetry pruning during generation** (keep only one of (S,P)/(P,S) for E and I):

* A and O remain ordered: `2 * L*(L-2)`.
* E and I become unordered pairs: `2 * (L choose 2 minus n base-term pairs)`.

  * `(L choose 2) = L(L-1)/2`.
  * Disallowed same-base-term pairs count = `n` (each base term contributes {T,¬T}).
  * So E+I total = `2 * (L(L-1)/2 - n) = L(L-1) - 2n`.
* Combined total after both prunes:

  * `A+O = 2*L*(L-2)`
  * `E+I = L(L-1) - 2n`
  * Sum = `2L(L-2) + L(L-1) - 2n`.
  * With `L=2n`: `2*(2n)(2n-2) + (2n)(2n-1) - 2n = 8n(n-1) + 4n^2 - 2n - 2n = 12n^2 - 12n`.
  * So: **`12n(n-1)` generated statements**.

**After equivalence collapsing (search over class reps)**
Equivalence mapping does two things:

1. A is treated as E with complemented predicate; O as I with complemented predicate.
2. E/I symmetry is already handled, but equivalence also means A/O don’t add new logical content.

Result: the search list is approximately the number of unique canonical E/I keys. Under your pruning, this is:

* Unique E keys = unordered literal pairs excluding same-base-term pairs = `L(L-1)/2 - n`.
* Unique I keys = same count.
* Total unique classes ≈ `2 * (L(L-1)/2 - n) = L(L-1) - 2n`.
* With `L=2n`: `2n(2n-1) - 2n = 4n^2 - 4n = 4n(n-1)`.

So, at a high level:

* **Generated statements** after prunes: about **`12n(n-1)`**.
* **Search reps** after equivalence collapsing: about **`4n(n-1)`**.
* That’s a further **~3× reduction** for the search loop compared to generated statements, and a larger reduction compared to naive enumeration.

(These are “structure counts” before semantic pruning/memoization; later stages reduce far more.)

### 1.8 ELI5: why we prune and bucket equivalents

Think of each statement as a **sentence template** about two groups, like:

* “All cats are mammals” (A)
* “No cats are reptiles” (E)
* “Some cats are mammals” (I)
* “Some cats are not mammals” (O)

Now imagine we have `n` named groups (A, B, C, …) and we also allow talking about **“not-A”**, **“not-B”**, etc. That means there are **`2n` choices** for the subject and **`2n` choices** for the predicate.

If we generate everything naively, the number of sentences explodes.

What we do to keep it manageable:

1. **Drop useless/trivial pairs**

   * We refuse to generate statements that compare a term to itself (or its own “not” form), because those don’t make good puzzles and add noise.
2. **Don’t generate duplicates we already know are the same**

   * For “No S are P” (E) and “Some S are P” (I), swapping S and P doesn’t change the meaning. So we only keep one ordering.
3. **Bucket different phrasings that mean the same thing**

   * “All S are P” (A) can be rewritten as “No S are not-P” (E).
   * “Some S are not P” (O) can be rewritten as “Some S are not-P” (I).
   * So A/O don’t add new *logic*—they’re mostly alternate wording.

Result: later search iterates only **one representative per meaning**, not every wording.

#### Concrete growth examples

Below are counts for how many statements we’d deal with at each step. This is just the syntax stage—before semantics and search.

* **term_count = 4**

  * Naive (no pruning): **224**
  * After removing same-base-term pairs: **192**
  * After also removing E/I swapped duplicates: **144**
  * After bucketing equivalents (search reps): **48**

* **term_count = 5**

  * Naive: **360**
  * After same-base-term pruning: **320**
  * After also E/I swap pruning: **240**
  * Search reps: **80**

* **term_count = 6**

  * Naive: **528**
  * After same-base-term pruning: **480**
  * After also E/I swap pruning: **360**
  * Search reps: **120**

The key takeaway a non-coder should notice:

* Adding 1 term increases the naive count a lot.
* The “search reps” count grows much more slowly, because we’re focusing on **unique meanings**.

### 1.9 How syntax feeds the semantic stage

The syntax stage produces two critical things the semantic stage needs:

1. **A complete catalog** (`all_statements`) so any `statement_id` can be translated back into a human-readable sentence.
2. **Equivalence classes + representatives** so later phases can:

   * Compute semantic effects for every statement (for storage/debug), but
   * Run the search over **representatives only** (one per meaning) to avoid redundant work.

Next step (semantic): for each `statement_id`, compute and store the semantic constraints it imposes (what regions become impossible, and what regions must be nonempty), and map those constraints into compact bitmasks for fast search.
