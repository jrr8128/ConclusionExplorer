# Game of Logic — Phase 1 Presearch Preparation Trace

> Scope: how the search-ready **state**, **canonicalization key**, and **memo table** are defined and used.

## 0. What this stage sets up (ELI5)

Before search starts, we decide:

* what “the current situation” looks like in memory (**semantic_state**),
* how to turn that situation into a compact “fingerprint” (**canonical_key**),
* how to remember fingerprints we’ve already explored (**memo**) so we don’t redo work.

---

## 1. `semantic_state`: the search state

### 1.1 Meaning (plain-English)

* `allowed`: which “boxes/regions” are still possible.
* `req_bits`: which “must-have-a-witness” requirements are currently active.

This is the only data that needs to change as the search adds premises.

### 1.2 Data layout

From `semantic_state.hpp`:

* `semantic_state.allowed` is a `region_mask` (fixed-size mask over regions).
* `semantic_state.req_bits` is an array of 64-bit words.

### 1.3 Rules

* **Rule:** `allowed` must never have bits set outside `all_regions`.
* **Rule:** `req_bits` is indexed by **requirement_index (rid)**, not by `statement_id`.
* **Rule:** unused high words/bits in both masks must stay 0 (otherwise canonicalization/hash becomes inconsistent).

### 1.4 Initial state (start of search)

* `allowed = sem_space.all_regions` (everything is possible before any premises).
* `req_bits = 0` (no witness requirements are active before any I/O premise is added).

---

## 2. `apply_premise`: the only state transition

### 2.1 Inputs

* `state` (mutable)
* `premise_id prm_id` (same numeric domain as `statement_id`)
* `semantic_space sem_space` (lookup tables)

### 2.2 Exact step order

1. Load `forb_mask = forbidden_regions_by_statement[prm_id]`.
2. Compute `new_allowed = old_allowed & ~forb_mask` word-by-word.

   * Track:

     * whether any bit remains set (if none → inconsistent)
     * whether allowed changed (if no → skip copying)
3. If premise has a requirement (`rid >= 0`): set bit `rid` in `state.req_bits`.
4. If allowed changed and/or a requirement was added:

   * For each active requirement bit `rid`:

     * check whether `(allowed_view ∩ req_mask_by_req_index[rid])` is empty.
     * if empty → inconsistent.
5. If allowed changed and not inconsistent, commit `state.allowed = new_allowed`.
6. Return:

   * `inconsistent` / `no_change` / `changed`.

### 2.3 Why this is lean

* No dynamic allocation.
* No loops over regions; only loops over 64-bit mask words.
* Requirement checking iterates only set bits via `ctz` (fast sparse iteration).

### 2.4 Worked bitmask examples (term_count = 3)

There are `2^3 = 8` regions, indexed `0..7`. Each region index is a 3-bit truth assignment:

* bit0 = term0 (A), bit1 = term1 (B), bit2 = term2 (C)
* Example: region `5 = 101₂` → A=true, B=false, C=true.

A `region_mask` is a set of region bits. For term_count=3 it fits in one 64-bit word; the low 8 bits matter.

#### Starting state

* `allowed = 11111111₂` (all regions possible)
* `req_bits = 0` (no nonempty requirements active)

#### Apply E(A,B): “No A are B”

This forbids regions where A=true AND B=true.

* Regions: `3 = 011₂`, `7 = 111₂`
* `forbidden = bit(3) | bit(7) = 10001000₂`
* Update: `new_allowed = allowed & ~forbidden`

  * `new_allowed = 11111111₂ & 01110111₂ = 01110111₂`
    Meaning: regions 3 and 7 are removed from what’s possible.

#### Apply I(A,C): “Some A are C”

This adds a requirement: at least one region with A=true AND C=true must remain possible.

* Regions: `5 = 101₂`, `7 = 111₂`
* `req_mask = bit(5) | bit(7) = 10100000₂`
* Table mapping:

  * `rid = req_index_by_statement_id[sid_of_I(A,C)]`
  * `req_mask_by_req_index[rid] = 10100000₂`
* State update: set `req_bits[rid] = 1`.

Consistency check for that requirement:

* Requirement is satisfiable iff `(allowed & req_mask) != 0`.
* Here: `allowed = 01110111₂`

  * `allowed & req_mask = 01110111₂ & 10100000₂ = 00100000₂` (nonzero)
    So it’s still consistent: region 5 can witness the “Some …” claim.

If later `allowed` also loses region 5 (and 7 is already forbidden), then:

* `allowed & req_mask = 0` → inconsistent immediately.

#### Why bitmasks are fast here (problem-specific)

* Each 64-bit AND/OR updates or checks **64 regions at once**.
* Search is the hot path: it does millions of “add premise → update state → prune” steps.
* Precomputing masks once (semantic stage) avoids recomputing region logic during search.
* State is tiny and contiguous (a few 64-bit words), so it stays cache-friendly and branch-light.

## 3. `is_inconsistent`: pruning test

A state is impossible if either:

1. `allowed` has no set bits, OR
2. some active requirement mask has no overlap with `allowed`.

(This mirrors the checks inside `apply_premise`, but is callable independently.)

---

## 4. `canonical_key`: turning state into a fingerprint

### 4.1 Purpose

A `canonical_key` is the **hashable snapshot** of a state used by memoization.

### 4.2 Current implementation

From `canonicalizer.cpp`, `canon::make_key(state)` currently copies:

* `allowed`
* `req_bits`

### 4.3 Rules for canonicalization to be valid

* **Rule:** two states that are logically identical must produce identical keys.
* **Rule:** all unused bits must be zeroed consistently (or hashes will diverge).

  * For `allowed`: words beyond `active_words` must be 0; bits beyond `region_count` must be 0.
  * For `req_bits`: words beyond `sem_space.req_words` must be 0; bits beyond the max rid must be 0.

---

## 5. `memo`: what is remembered and why

### 5.1 What memo keys on

`memo_key = (canonical_key, next_min_id)`

Meaning:

* `canonical_key`: what the world looks like (allowed + active requirements).
* `next_min_id`: the smallest premise ID the search is allowed to pick next.

`next_min_id` matters because it removes permutation duplicates:

* `{p3, p7}` and `{p7, p3}` should be treated as the same set.
* By forcing premises to be added in increasing ID order, the search explores each set once.

### 5.2 What memo stores

`seen[memo_key] = best_depth_left_seen`

Interpretation:

* If we have already reached the same `(state, next_min_id)` with **at least as much remaining depth**, then reaching it again with less remaining depth can’t produce anything new.

### 5.3 Prune rule (exact)

* `should_prune(state, next_min_id, depth_left)` returns true iff:

  * key exists, and
  * `depth_left <= stored_depth_left`.

### 5.4 Record rule (exact)

* `record_seen` inserts the key if absent.
* If present, it overwrites only when `depth_left` is larger.

---

## 6. Sizing rule for `req_bits`

`semantic_state.req_bits` must be sized for **requirement_index (rid)**, not for the number of selected premises.

* Correct fixed-size choice: `std::array<uint64_t, MAX_REQ_WORDS>` where `MAX_REQ_WORDS = ceil(MAX_REQS/64)`.
* Per-run work stays small by iterating only `sem_space.req_words` words (and/or scanning only set bits).

**Rule:** always keep words beyond `sem_space.req_words` zeroed so canonical keys don’t diverge.

---

## 7. How this feeds search

Search will:

1. create an initial `semantic_state`.
2. repeatedly call `apply_premise` as it tries adding premises.
3. use `canon + memo` to avoid re-exploring the same state.
4. use `next_min_id` to avoid exploring the same premise set in different orders.
